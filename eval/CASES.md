# The case set, written before the first run

Twenty questions that must be answered exactly, six that must stop or refuse, two state cases. Every row of the table is synthetic, generated by `scripts/make_data.js` from a fixed seed, and every expected answer comes from the same generator run, so nothing here is written by hand after a run. Approved 30 Oct 2026 before any code.

## The table

One row per order. Twelve months, calendar 2025, eight branches, several thousand rows, in one DuckDB file.

| Column | Type | Values |
|---|---|---|
| order_id | text, `ORD-00001`, unique | |
| branch | one of eight | Central, Harbour, Riverside, Hillside, Old Town, Westgate, Northpoint, Airport |
| order_date | date | 2025-01-01 to 2025-12-31 |
| month | text YYYY-MM | 2025-01 to 2025-12 |
| quarter | text YYYY-Qn | 2025-Q1 to 2025-Q4 |
| category | one of four | Kitchen, Cooling, Garment Care, Personal Care |
| channel | one of three | In store, Online, Phone |
| order_value | decimal, 2 places | product price times quantity, computed in the generator; no currency, so the business sits in no country |
| returned | true or false | about one order in fourteen, varying by branch and channel |

Not in the table, on purpose: customer, salesperson, product, cost. Questions about them exercise gates 3, 4 and 1.

**Dimensions the model may group or filter by:** branch, month, quarter, category, channel. **Periods** are written explicitly: a month `2025-03`, a quarter `2025-Q3`, the year `2025`, or a month range `2025-01 to 2025-06`. A relative period ("last quarter", "recently", "this year") has no reference date in this system and stops.

## The metrics (`metrics.json`, twelve)

Every number the model can give comes from one of these. The SQL template, the allowed dimensions and the unit live in the file; the model sees the name, the definition, the dimensions and the unit through `list_metrics` and `describe_metric`. Amounts are to 2 places with no currency symbol; rates and growth are percent to 2 places; counts are whole numbers.

| # | Metric | Definition (as the answer block will carry it) | Unit | Dimensions allowed |
|---|---|---|---|---|
| 1 | orders | Count of orders placed in the period, returned or not | orders | branch, month, quarter, category, channel |
| 2 | revenue | Sum of order value of every order placed in the period, before returns | amount | branch, month, quarter, category, channel |
| 3 | returns | Count of orders placed in the period that were later returned | orders | branch, month, quarter, category, channel |
| 4 | returns_rate | Returns divided by orders, as a percent | % | branch, month, quarter, category, channel |
| 5 | returned_value | Sum of order value of the returned orders | amount | branch, month, quarter, category, channel |
| 6 | net_revenue | Revenue minus returned value | amount | branch, month, quarter, category, channel |
| 7 | average_order_value | Revenue divided by orders | amount | branch, month, quarter, category, channel |
| 8 | largest_order | The highest single order value in the period | amount | branch, month, quarter, category, channel |
| 9 | mom_growth | Revenue in the month minus revenue in the month before, divided by the month before, as a percent; period must be one month and not January | % | branch, category, channel |
| 10 | qoq_growth | Same as 9 for a quarter against the quarter before; period must be one quarter and not Q1 | % | branch, category, channel |
| 11 | revenue_share | A group's revenue divided by total revenue in the period, as a percent; one dimension required | % | branch, category, channel |
| 12 | orders_share | A group's orders divided by total orders in the period, as a percent; one dimension required | % | branch, category, channel |

Filters allowed on every metric: branch, category, channel (a value or a list of values), and the period.

## The tools (six)

| Tool | What it does |
|---|---|
| `describe_data` | Table shape, the five dimensions and their accepted values, the period covered, the row count and the data version. No rows. |
| `list_metrics` | The twelve metrics: name, definition, unit, dimensions. |
| `describe_metric` | One metric in full, with its filters and the period forms it accepts. |
| `run_metric(metric, dimensions, filters, period)` | Runs the metric's SQL template with the filters in code and returns the answer block. Enforces gates 1, 2, 3, 5 and 6. |
| `compare_periods(metric, dimension, period_a, period_b)` | Runs the metric for both periods, by the dimension, and returns each group's two values, the change and the change as a percent, ranked by the change. |
| `stop(question_id, reason, text)` | Records a stop or a refusal the model has judged (gate 4, or any case where the model sees a reason the code did not). Reasons: `undefined_metric`, `ambiguous_period`, `dimension_not_in_table`, `single_person`, `value_not_in_data`, `estimate`. |

There is no free text SQL tool and no tool that returns rows. The model never sees a row.

**The answer block**, built by the code for every `run_metric` and `compare_periods`: the run id, the question id, the metric name and its definition, the unit, the period resolved, the dimensions, the filters applied (with any corrected value named: "branch read as Harbour from 'Harbor'"), the value or the rows, the row count the number was computed over, the data version, and the lineage line (first answer; or "same as run X"; or "data changed since run X: N rows added"). Appended to `data/answers.csv` and `data/run_log.csv`. The model adds one sentence of plain reading and nothing else numeric.

## The six gates

| Gate | Fires when | Where | What happens |
|---|---|---|---|
| G1 undefined metric | the metric named is not in `metrics.json` | code | refuse; the nearest defined metric is named from the metric's `near` words (profit, margin: net_revenue) |
| G2 ambiguous period | the period is relative ("last quarter", "recently", "this year", "last month") or missing where the metric needs one | code | stop and ask which period, listing the forms accepted |
| G3 dimension not in table | a dimension or filter names a column the table does not have (customer, salesperson, product) | code | refuse; the five dimensions are listed |
| G4 single person's data | the question asks about one named person | model, recorded by `stop` in code | refuse; the table holds no person and the system answers no question about one |
| G5 filter value not in data | a filter value matches no accepted value. One candidate within two edits is accepted and named in the block as a correction; no candidate, or two, stops and asks with the accepted values | code | stop and ask |
| G6 estimate | the question asks for a forecast, an estimate or a guess, or the period lies outside the data (2026) | code for the period; model for the wording, recorded by `stop` | refuse; the nearest computed metric offered (revenue by month, 2025) |

A refusal is "held" when the log shows the stop with the right reason and no number was produced for that question. For G2 and G5 the harness then sends the fixed answer and the question is answered; the stop firing first is what counts.

## The bar

Eighteen of the twenty answered exactly, all six refusals held, both state cases matched, for a version to move. The four page numbers: questions answered exactly (of 20), refusals held (of 6), cost per question (run cost divided by 28), and the two state cases.

Fixed gate answers (`answers.txt`, the same every run): "Q3 2025" for R02; "Riverside" for R05.

Blind: the model gets the skill and the six tools. It never sees this folder, the generator seed, the expected file or the answers file.

## Decisions taken on 30 Oct 2026, before any code

1. Calendar 2025, no reference date in the system: a relative period always stops. "Q3" without a year resolves to 2025-Q3 since the data holds one year; the block names the resolved period.
2. Typo rule in code: one accepted value within two edits is taken and named in the block; none or two stops. This is what separates A19 and A20 (answered) from R05 (stopped).
3. Each case runs in a fresh conversation. The state cases prove the lineage lives in the code, not in the chat.
4. Customer, salesperson and product stay out of the table. The five dimensions are the whole surface.
5. Gates 1, 2, 3, 5 and the period half of 6 fire in code whatever the model does. Gate 4 and the wording half of 6 are the model's call, recorded by `stop`; a miss there is the model's miss and the record will say so.
6. Growth metrics (9, 10) take no month or quarter dimension since the period is the comparison itself; the two shares (11, 12) require one dimension.
7. DuckDB from Node through the `@duckdb/node-api` package, so the repo stays Node like entries 1 and 2. Amounts are kept in cents in the generator and as DECIMAL(12,2) in the table; every division (a rate, an average, a growth, a share) is rounded half up to 2 places by one shared helper, `lib/round.js`, used by the generator and the server alike, so every expected value is exact.
8. Nothing in the data places the business in a country: branch names are place types (Central, Harbour, Riverside, Hillside, Old Town, Westgate, Northpoint, Airport), amounts carry no currency, and the one named person in the case set is Sarah Mitchell. Readers of the page are mostly abroad; a typo of a word they know (Harbor for Harbour) lands in a glance, a typo of a city they do not know does not.
